# 무엇을 어디에 두는가

새 룬, 새 수치, 새 계산 방식을 넣을 때 **어느 파일을 여는지** 를 정한다.
막히면 [질문 세 개](#질문-세-개로-정해진다)만 답하면 자리가 나온다.

이 문서가 필요한 이유는 하나다. 자리를 그때그때 정하면 같은 사실이 두 곳에 생기고,
두 곳에 생긴 순간부터 **둘 중 하나는 반드시 낡는다.** 낡은 쪽이 이용자가 보는 쪽이었던
적이 여러 번 있었다. 그래서 규칙은 "잘 정리하자" 가 아니라 **자리를 하나로 못박는 것**이다.

---

## 질문 세 개로 정해진다

**1. 게임이 정한 것인가, 우리가 정한 것인가?**

| | 자리 |
|---|---|
| 게임이 정한 것 (툴팁 수치, 지속시간, 임계값) | **데이터** (`data/*.json`, `src/runes-data.mjs`) |
| 우리가 정한 것 (수식, 해석, 근사) | **코드** (`src/*.mjs`) + 테스트 |

경계가 헷갈리는 자리가 하나 있다: **수식의 파라미터는 게임이 정한 것이다.**
"쿨 4초·지속 10초·5스택" 은 데이터고, 그걸로 가동률을 구하는 식은 코드다.
파라미터를 코드에 박으면 게임이 패치돼도 데이터 기여자가 못 고친다.

**2. 항목 하나에 붙는가, 전체에 걸리는가?**

| | 자리 |
|---|---|
| 이 룬/아티팩트/숙련 하나 | 그 항목 옆 (`uncounted`, `note`, `evidence`) |
| 도구 전체 | `data/limits.json` |

**3. 값인가, 값에 대한 말인가?**

값과 그 근거는 **같은 자리에** 둔다. 값은 데이터에, 근거는 코드 주석에 — 이렇게 갈라두면
데이터만 보는 사람이 그 값을 믿어도 되는지 판단할 수 없다. `note`·`evidence`·
`disabledReason` 이 그래서 있다.

## 자주 있는 일

### 새 룬이 추가됐다

1. `src/runes-data.mjs` 에 항목을 넣는다 — `name`·`slot`·`grade`·`desc`(게임 원문 그대로).
2. 상시 효과는 `alwaysOnAttackPercent`·`alwaysOnDamagePercent`·`alwaysOnExtra`.
3. 조건부가 있으면 `conditionalRaw` 에 **툴팁의 기본 수치**를 적는다.
   상호 배타인 분기를 더하지 마라 — 더한 값은 게임 어디에도 없는 숫자다(테스트가 막는다).
4. 조건부를 제대로 모델링하려면 `data/rune-conditionals.json` 의 `RUNE_CONDITIONALS`.
   조건부가 정말 없으면 `NO_CONDITIONALS` 에 넣어 "확인했다" 를 남긴다.
5. 계열(침식·저주·용의 문장 등)이면 해당 목록에도 넣는다.

**손으로 목록을 만들지 마라.** 항목의 성질에서 계산되는 목록은 파생시킨다 —
무방비 룬 목록이 손 목록이었다가 실제로 갈라졌다(`VULNERABLE_RUNES` 참고).

### 새 수치가 생겼다

`evidence` 없이 넣지 마라. 게임에 적혀 있으면 `{ "type": "tooltip", "date": "..." }` 로 끝난다.
재본 값이면 `measured` + 무엇을 어떻게 쟀는지. **근거를 지어내지 마라** — 틀린 수치는
언젠가 드러나지만 가짜 근거는 검증된 것처럼 보여서 더 나쁘다.

### 새 계산 방식(수식)을 넣는다

1. 수식은 **코드**에 이름 붙은 함수로. `data/` 에 표현식을 넣지 마라 — 결국 `eval` 이다.
2. `src/build-evaluator.mjs` 의 `EXPECTED_FROM_PARAMS` 에 이름과 **필수 파라미터**를 등록한다.
   이름만 등록하고 파라미터를 빼먹으면, 데이터에서 파라미터가 누락돼도 검증을 통과하고
   기대값이 NaN 을 거쳐 조용히 0 이 된다.
3. 파라미터는 데이터에 둔다(질문 1).
4. 게임 시스템 상수는 `data/rune-conditionals.json` 의 시스템 키
   (`DRAGON_SIGIL`·`TRANSCEND_EMBLEM`·`EROSION_SYSTEM`) 옆에.

### 계산에 못 넣는 효과다

`field` 대신 `uncounted` 에 **왜 못 넣는지** 를 적는다. 둘을 같이 쓰면 검증기가 막는다.
"값이 빠졌다" 와 "계산할 자리가 없다" 는 다르다 — 전자는 채우면 되고 후자는 채워도 자리가 없다.
도구 전체에 걸리는 한계면 `data/limits.json` 이다.

### 새 effects 경로가 필요하다

`data/effect-fields.json` 에 없는 경로는 **에러 없이 계산에서 빠진다.**
경로를 새로 만들려면 `calculator.mjs` 의 항 구조까지 봐야 하므로, PR 이 아니라 이슈로 제안한다.

## 파생시킬 것 · 손으로 적을 것

목록을 손으로 적기 전에 **그 목록이 이미 있는 데이터에서 계산되는지** 보라.

| 파생시킨다 (손 목록 금지) | 이유 |
|---|---|
| 무방비 룬 목록 | `requiresVulnerable` 과 `break.*` 필드에서 나온다 |
| `EXPECTED_FROM_NAMES` | `EXPECTED_FROM_PARAMS` 의 키다 |
| `LIMITS.md` · `limits.html` · `HELP-WANTED.md` | `data/` 에서 생성된다 |
| 룬 이름 검증 | `runes-data.mjs` 가 이름의 진실이다 |
| 「계산 밖」 목록의 페널티 문장 (`src/rune-uncounted.mjs`) | `NEGATIVE_TRAITS` 에서 나온다 |
| 유틸 항목이 이득인가 손해인가 (`src/stat-polarity.mjs`) | `STAT_BETTER_WHEN` 에서 나온다 |

손으로 적어야 하는 것은 **데이터에서 계산할 수 없는 분류**뿐이다 — 부정 효과 목록처럼
사람의 판단이 들어가는 것(`NEGATIVE_TRAITS` 는 '감소' 로 훑으면 이득까지 딸려와 자동화가 안 된다).

그 손 목록은 **한 벌이어야 한다.** 화면에 "이 룬은 나쁜 점이 있다" 고 적는 자리가 둘이면
둘이 서로 다른 룬을 가리키게 된다. 실제로 그랬다 — 페널티 문장을 설명문에서 정규식으로
뽑던 때, 그쪽은 공허·위엄·다가옴+·무형·추적자를 페널티로 봤고 `NEGATIVE_TRAITS` 에는
그 다섯이 하나도 없었다. 앞의 넷은 쿨감처럼 **이득이 줄어드는** 문장이었고, 진짜였던
추적자는 배지도 필터도 못 받고 있었다.

## 두 벌이 되기 쉬운 자리

지금까지 실제로 갈라졌던 곳이다. 여기에 무언가 적기 전에 반대편을 먼저 확인해라.

- **코드 주석 ↔ 데이터** — 주석에 수치를 적으면 데이터를 고쳐도 주석은 안 고친다.
  주석에는 "왜" 만 적고 "얼마" 는 데이터를 가리켜라.
- **문서 ↔ 데이터** — 한계·모집 문서는 전부 생성물이다. 손으로 고치지 마라.
- **입력칸 힌트 ↔ effects** — 힌트 산문에 숫자를 박으면 도움말이 계산과 다른 말을 한다.
- **분류 목록 ↔ 항목 속성** — 위의 파생 표를 보라.

## 순서가 있다

데이터에 키를 새로 넣고 그것을 코드가 쓰기 시작할 때는 **생성을 먼저** 해야 한다.

```bash
node tools/build-data.mjs     # data/ → src/gen/. 코드가 새 키를 쓰기 전에 먼저
node tools/validate-data.mjs
npm test
npm run build
```

`src/gen/` 은 커밋한다. 생성물이 원본과 어긋나면 테스트가 잡는다.

---

## 이 문서를 고쳐야 할 때

새 자리를 만들었으면 여기 한 줄 추가하고, **그 자리를 강제하는 검사**를 함께 넣어라.
검사 없는 규칙은 다음 사람이 모른다 — 이 저장소에서 규칙이 지켜지는 이유는 문서가 아니라
검증기와 테스트다. 규칙만 늘고 검사가 안 늘면 이 문서도 결국 낡은 문서가 된다.
